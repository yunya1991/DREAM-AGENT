# 飞书老板视图与 OKR 中联动设计

> 仓库：`DREAM-AGENT`
> 日期：`2026-06-08`
> 状态：draft
> 目标：在现有 `目标推进表` 已落地的基础上，补出一套“老板先看中文结果，再按需下钻到 OKR / workflow”的中联动方案，让目标层监控、OKR 对齐与关键提醒可以形成首批可落地闭环。

## 0. 文档元信息

本文档面向以下读者：

- 负责 Dream-Agent 目标推进与治理收口的维护者
- 需要在飞书中查看中文老板视图的使用者
- 负责飞书 Base、审批、workflow 与后续 OKR 联动的维护者
- 后续需要决定是否追加 dashboard 的产品与治理维护者

一句话定义如下：

> `飞书老板视图与 OKR 中联动` 是一套以 Base 为管理驾驶舱、以飞书 OKR 为目标主系统、以 workflow 为提醒与校验层的中间态方案，强调“先看状态与阻塞，再决定是否下钻与推动”。

## 1. 背景与问题定义

当前已经完成以下基础工作：

- `目标推进表` 已在真实 Base 中创建并写入首条记录
- `自动化任务监控` 表已经补齐审批相关监控字段
- 真实审批实例创建链路已经打通，后续将继续补实例回读与状态覆盖回写

但从“老板可用”和“目标管理收口”的角度看，仍有三个缺口：

### 1.1 现有目标推进表更像工程表，而不是老板视图

当前字段以英文锚点和自动化字段为主，虽然适合后续脚本回写，但不适合管理者直接打开阅读。

用户当前的真实诉求不是继续堆字段，而是：

- 打开即能看懂
- 先看到状态和阻塞
- 需要时再进入更深层的 OKR / workflow / 审批细节

### 1.2 目标推进表还没有和飞书 OKR 正式产品对齐

现有 `目标推进表` 可以表达：

- 当前目标推进状态
- 风险与 blocker
- 审批和执行摘要

但还不能回答：

- 这个目标对应的正式 Objective 是哪一个
- 目标推进表中的目标是否已完成 OKR 对齐
- 当前目标推进异常时，是否应该提醒负责人补 OKR 或修正状态

### 1.3 workflow 与 dashboard 需要分层判断是否进入首批

workflow 与 dashboard 都可能增强可用性，但价值不同：

- workflow 可以让“目标状态变化 -> 人被提醒 -> 负责人做动作”形成闭环
- dashboard 更适合目标规模变大后的图表化观察

因此本轮需要做清楚分层，而不是把所有能力一次铺满。

## 2. 设计目标

本设计的目标如下：

- 让 `目标推进表` 具备一个真正可读的中文老板视图
- 建立 `目标推进表 -> 飞书 OKR` 的正式联动锚点，而不是只在 Base 内模拟 OKR
- 把 workflow 提升到首批范围，但只承担提醒型和校验型职责
- 为后续 dashboard 预留字段和设计空间，但不把 dashboard 纳入首批落地

成功标准如下：

- 老板进入 Base 后能优先看到中文 `状态 + 阻塞` 视图
- 每个目标都能识别是否已对齐正式 OKR
- 当目标处于高风险、审批完成、或缺失 OKR 对齐时，workflow 能推动负责人处理
- 后续如果追加 dashboard，不需要推翻当前字段模型

## 3. 非目标与边界

本设计明确不做以下事项：

- 不把 Base 做成 OKR 正式主系统
- 不在本轮直接改写飞书 OKR 核心对象
- 不让 workflow 首批直接自动修改业务真状态
- 不在本轮强制建设 dashboard 图表面板
- 不重命名或推翻现有英文锚点字段，以免破坏脚本兼容

本设计边界如下：

- Base 负责老板视角、执行摘要与联动锚点
- 飞书 OKR 正式产品负责目标主语义
- workflow 只做提醒与校验，不做自动改真状态
- dashboard 保留为第二阶段增强项

## 4. 设计原则

### 4.1 老板视图优先于工程字段暴露

老板视图必须先服务于“看懂”，而不是先暴露技术字段。

因此首屏应当：

- 以中文字段表达为主
- 优先展示 `状态 + 阻塞`
- 将审批、workflow、OKR 锚点隐藏在次级层

### 4.2 OKR 是主系统，Base 是驾驶舱

飞书 OKR 正式产品继续承载：

- Objective / KR
- owner
- 对齐关系
- 目标管理节奏

Base 则承载：

- 当前推进状态
- blocker
- 风险
- 下一步动作
- 最近决策摘要

两者职责不同，不能双写成两套真相源。

### 4.3 workflow 首批只做提醒和校验

workflow 首批允许做：

- 状态变化提醒
- 异常校验提醒
- 对齐缺失提醒

workflow 首批不允许做：

- 自动修改目标真状态
- 自动改写 OKR 核心对象
- 自动覆盖人工填写的 blocker 或下一步动作

### 4.4 dashboard 只有在字段语义稳定后才值得做

只有当 `状态 / 阻塞 / 风险 / OKR对齐` 的口径稳定后，图表才有价值。

因此 dashboard 应当建立在现有模型稳定后，而不是先于模型建设。

## 5. 总体方案

### 5.1 方案定位：中联动

本轮采用 `中联动`，而不是轻联动或重联动。

其含义是：

- 比轻联动多做一层 workflow 推动
- 比重联动少做 dashboard 与复杂自动编排

最终形态如下：

- `目标推进表` 是老板与治理视角的中文驾驶舱
- 飞书 `OKR` 是正式目标系统
- workflow 把关键状态变化转成提醒和校验动作
- dashboard 暂不进入首批实施

### 5.2 用户视角路径

用户在飞书中的使用顺序应为：

1. 先打开 `目标推进表` 的中文老板视图
2. 先看当前状态与阻塞
3. 若需要目标管理细节，再看 OKR 对齐情况
4. 若需要推进动作，再根据 workflow 提醒进入处理

不能让老板一上来就看到大量技术字段、审批细节或图表噪声。

## 6. 老板视图设计

### 6.1 视图名称

建议在 `目标推进表` 上新增中文视图：

- `老板视图（状态与阻塞）`

这是首屏主视图，应优先于现有工程视图出现。

### 6.2 首屏字段顺序

老板视图首屏应只保留以下 7 个中文字段，并按此顺序展示：

- `目标名称`
- `当前状态`
- `当前阻塞`
- `风险等级`
- `下一步动作`
- `OKR对齐`
- `最近决策摘要`

其中：

- `当前状态`
- `当前阻塞`

是首屏最重要的两个字段。

### 6.3 中文老板字段层

建议补充或映射出以下中文可读字段：

- `目标名称`
- `当前状态`
- `当前阻塞`
- `风险等级`
- `下一步动作`
- `最近决策摘要`
- `OKR对齐`

这些字段是老板默认可见层。

### 6.4 工程锚点层

以下字段继续保留为工程锚点，但不默认暴露给老板：

- `goal_id`
- `approval_status`
- `approval_instance_code`
- `current_phase`
- `goal_progress`
- `workflow_signal`
- `last_workflow_run_at`
- `okr_objective_id`
- `okr_objective_title`
- `okr_owner`
- `okr_sync_status`
- `okr_last_sync_at`

### 6.5 字段维护方式

建议字段按下列方式维护：

自动投影：

- `当前状态`
- `风险等级`
- `最近决策摘要`
- `approval_status`
- `current_phase`
- `goal_progress`
- `okr_sync_status`
- `last_workflow_run_at`

人工维护：

- `当前阻塞`
- `下一步动作`
- `目标名称` 的中文业务表述优化
- 必要时人工确认 `OKR对齐`

原因是：

- 状态和风险适合系统聚合
- 阻塞和下一步动作往往最需要人的语义判断

## 7. 目标推进表与 OKR 映射

### 7.1 联动策略

采用：

- `单向主从 + 最小回写`

即：

- 飞书 OKR 是主系统
- Base 从 OKR 拉目标层锚点
- Base 叠加执行层与审批层事实
- Base 不直接反向改写 OKR 核心对象

### 7.2 映射规则

建议的字段映射如下：

- `目标名称` <- `Objective 标题`
- `okr_objective_id` <- `Objective ID`
- `okr_objective_title` <- `Objective 标题`
- `okr_owner` <- `Objective owner`
- `OKR对齐` <- 是否已绑定有效 Objective
- `当前状态` <- Base 依据审批 / 阶段 / blocker / 风险综合投影
- `当前阻塞` <- Base 人工维护为主
- `风险等级` <- Base 投影
- `下一步动作` <- Base 人工维护
- `最近决策摘要` <- 审批 / workflow / 人工备注聚合

### 7.3 `OKR对齐` 的中文枚举

老板视图中的 `OKR对齐` 不应直接显示技术 ID，而应显示中文枚举：

- `已对齐`
- `待补OKR`
- `待同步`
- `对齐异常`

这样用户无需理解 OKR 对象模型，也能看懂当前状态。

### 7.4 一致性规则

必须满足以下一致性约束：

- 没有有效 `okr_objective_id` 时，`OKR对齐` 不能显示为 `已对齐`
- 目标已经进入推进中但尚未绑定 Objective 时，应显示 `待补OKR`
- OKR 锚点存在但同步失败时，应显示 `对齐异常` 或 `待同步`

## 8. workflow 首批设计

### 8.1 workflow 的角色

workflow 在本轮进入首批，但职责仅限于：

- 提醒型
- 校验型

workflow 不是执行真源，也不是自动改状态引擎。

### 8.2 首批 3 条规则

#### 规则 1：阻塞升级提醒

触发条件：

- `当前阻塞` 非空
- 且 `风险等级 = high`

动作：

- 提醒 `goal_owner`
- 如存在 `okr_owner`，同时提醒 `okr_owner`

目标：

- 尽快暴露红灯目标，避免长期静默卡死

#### 规则 2：审批完成后提醒更新目标

触发条件：

- `approval_status` 从 `pending` 变为终态

动作：

- 提醒负责人检查并更新：
  - `当前状态`
  - `下一步动作`
  - `OKR对齐`

目标：

- 让审批结果真正转成推进动作，而不是停留在审批单中

#### 规则 3：OKR 对齐缺失提醒

触发条件：

- 目标已进入推进中
- 但 `OKR对齐 != 已对齐`

动作：

- 提醒负责人补绑 Objective 或说明异常原因

目标：

- 防止 Base 中的目标推进与正式 OKR 体系脱节

### 8.3 workflow 禁止事项

首批 workflow 禁止：

- 自动改写 `当前状态`
- 自动改写 `当前阻塞`
- 自动改写飞书 OKR 核心对象
- 自动改写 GitHub 真状态

这能避免自动化把人类语义字段“写死”，也避免双向写冲突。

## 9. dashboard 取舍

### 9.1 为什么不进首批

dashboard 本轮不进首批，原因如下：

- 当前最重要的是“打开就能看懂”
- 目标数量与状态规模还不足以支撑图表价值
- 如果先做图，很可能掩盖字段语义尚未稳定的问题

### 9.2 预留的第二阶段图表位

虽然不首批实施，但建议为后续预留两个图表方向：

- `目标状态分布`
- `高风险 / 有阻塞目标清单`

这样后续若老板确实需要图表，可以直接建立在现有字段模型之上。

## 10. 数据流与职责边界

### 10.1 OKR -> Base

从 OKR 拉入：

- Objective 锚点
- owner
- 标题
- 对齐关系

不拉入：

- 执行细节
- 审批事实
- blocker 与推进动作

### 10.2 GitHub / 审批 / 自动化 -> Base

从执行与审批侧回写：

- `approval_status`
- `最近决策摘要`
- `current_phase`
- `goal_progress`
- 其他执行层投影字段

### 10.3 人工 -> Base

由负责人维护：

- `当前阻塞`
- `下一步动作`
- 必要时的中文业务表述修正

## 11. 实施建议

建议按以下顺序落地：

1. 在 `目标推进表` 上补中文老板字段与 `老板视图（状态与阻塞）`
2. 增加 OKR 联动锚点字段
3. 定义并接入 `OKR对齐` 中文枚举逻辑
4. 建立首批 3 条 workflow
5. 观察实际使用，再决定是否进入 dashboard 阶段

## 12. 验收标准

本轮完成后，应满足：

- Base 中存在一个中文 `老板视图（状态与阻塞）`
- 老板视图首屏能直接看到 `状态 + 阻塞`
- 每个目标能识别是否已对齐正式 OKR
- workflow 能对高风险 blocker、审批完成、OKR 缺失发出有效提醒
- 现有自动化与审批脚本不因新增中文层而失效

## 13. 风险与控制

主要风险如下：

- Base 和 OKR 都承担真相源，导致双写冲突
- workflow 过度自动化，误改业务字段
- 中文老板字段与英文锚点字段口径不一致

对应控制策略：

- 明确 OKR 为主系统，Base 为驾驶舱
- workflow 首批只做提醒和校验
- 中文字段尽量由英文锚点投影，人工字段只保留 blocker 与下一步动作

## 14. 完成后的系统形态

本设计完成后，系统应达到以下形态：

- 飞书 Base 提供可直接阅读的中文老板视图
- 飞书 OKR 提供正式目标主语义
- workflow 负责把关键状态变化转成推进动作提醒
- dashboard 仍为后续增强项，而不是当前主路径
- 用户先看目标与阻塞，再决定是否进入 OKR / workflow / 审批细节
