# 飞书目标驱动进度监控与风险审批设计

> 仓库：`DREAM-AGENT`
> 日期：`2026-06-07`
> 状态：draft
> 目标：在现有 GitHub x 飞书协作闭环基础上，建立“目标驱动的实时进度监控 + 风险审批闸门”机制，让飞书既能承接自动化执行的目标视图，也能在高风险分叉与关键节点上承接人工决策。

## 0. 文档元信息

本文档面向以下读者：

- 负责 Dream-Agent 协作编排与治理收口的维护者
- 负责 GitHub Actions、bridge 与结构化评论的自动化维护者
- 负责飞书 Base / 审批 / 进度资产设计与接入的维护者
- 需要通过飞书实时监控进度并在关键时刻拍板的用户

一句话定义如下：

> `飞书目标驱动进度监控与风险审批` 是在 GitHub 作为执行真源的前提下，为 Dream-Agent 增加一套“目标推进可视化 + 高风险选择审批 + 超时保守续跑”的协作控制层。

## 1. 背景与问题定义

当前协作闭环已经补齐了以下基础能力：

- GitHub 侧已具备 `implementation_status / platform_status / governance_status / automation_status` 四层状态模型
- 飞书 Base 已具备自动化任务监控与 `pause / retry` 最小远程干预能力
- GitHub -> 飞书状态同步与飞书 -> GitHub 动作回写已完成第一轮真实联调

但随着自动化继续推进，出现了新的协作需求：

### 1.1 仅有任务监控，不足以支撑“目标驱动”查看

当前飞书 Base 更像任务级状态板，能看到：

- 某个 task 当前状态
- 当前 blocker
- 当前 next action

但还不能很好回答以下问题：

- 当前主目标整体推进到了哪一阶段
- 哪个目标被哪条任务卡住
- 哪个目标正在等待人工决策
- 哪个目标已经可以继续放大自动化

### 1.2 自动化运行中会出现“需要用户拍板”的分叉

自动化推进过程中会不断遇到类似决策：

- 多个实现方案都可行，但后续路线影响不同
- 是否从单任务扩展到多 agent
- 是否恢复暂停的自动化主链
- 是否执行回滚、重试或高风险覆盖

这些动作如果完全自动决策，容易放大风险；如果全部人工介入，又会拖垮推进效率。

### 1.3 需要形成“低风险自动推进，高风险审批决策”的平衡机制

用户已经明确偏好：

- 低风险分支自动按最佳方案执行
- 高风险分支和关键节点必须发起审批
- 审批超时后，优先走“最保守、可回滚、低扩张”的方案继续，而不是无限阻塞

这意味着飞书侧不应该只有监控表，还需要一个承接决策选择的正式通道。

## 2. 设计目标

本设计的目标如下：

- 建立“目标层 + 任务层”双层可视化监控结构
- 让飞书可以从目标维度实时查看自动化推进状态
- 在高风险分叉与关键节点上自动生成审批，承接用户拍板
- 将审批结果回写到任务状态和后续执行决策中
- 建立审批超时后的保守续跑机制，避免自动化无限等待
- 继续保持 GitHub 为执行真源，飞书为监控与决策面

成功标准如下：

- 用户在飞书中能先看目标，再下钻到任务
- 用户能明确识别哪些任务正在等待审批
- 自动化遇到高风险分叉时，能够生成带候选方案的审批单
- 审批结果能驱动 Dream-Agent 后续执行
- 审批超时后，系统能按保守策略继续或安全暂停

## 3. 非目标与边界

本设计明确不做以下事项：

- 不把飞书审批变成持续状态监控主界面
- 不把飞书升级成执行真源
- 不允许审批直接改写 GitHub checks 结果或治理真状态
- 不在本阶段接入复杂的多级审批、会签、串签流程
- 不在本阶段扩展到产物中台业务实现本身

本设计的边界如下：

- 进度监控主视图使用飞书 Base
- 审批只用于高风险分叉与关键节点，不承接全部日常选择
- 审批超时只允许执行保守续跑，不允许激进放权
- 第一版先聚焦单任务/单链路和少量关键节点

## 4. 设计原则

### 4.1 GitHub 是执行真源

GitHub 继续承载：

- PR
- checks
- workflow run
- 结构化评论
- governance handoff
- 代码与版本锚点

任何执行相关的真实状态，都必须以 GitHub 为准。

### 4.2 飞书进度表是目标驱动监控面

飞书 Base 的核心职责是：

- 展示目标推进情况
- 展示任务当前四层状态
- 展示 blocker / next action / risk level
- 展示当前是否等待审批

飞书进度表不直接替代 GitHub 执行。

### 4.3 飞书审批是人工决策闸门

飞书审批只在以下语义下存在：

- 自动化给出多个候选方案
- 需要用户对高风险动作拍板
- 需要用户决定是否跨入关键阶段

审批不是状态面板，而是“决策面板”。

### 4.4 低风险自动推进，高风险人工决策

系统默认策略必须是：

- 低风险：自动按最佳方案推进
- 高风险：发起审批等待用户决策
- 超时：先尝试保守续跑，否则安全暂停

### 4.5 先看目标，再看任务，再做决策

用户在飞书中的使用顺序应为：

1. 先看目标整体推进
2. 再下钻到具体任务
3. 当某任务进入高风险分叉时，再进入审批选择

不能让用户一上来就淹没在任务明细或审批单里。

## 5. 总体架构

系统分成四层：

### 5.1 GitHub 执行层

负责：

- workflow 执行
- PR / checks / comments
- 真实代码状态
- 版本锚点与回滚依据

### 5.2 Dream-Agent 编排层

负责：

- 判断当前任务推进状态
- 识别是否出现高风险分叉或关键节点
- 生成候选方案与推荐方案
- 读取审批结果并决定后续动作

### 5.3 飞书进度监控层

负责：

- 目标推进展示
- 任务推进展示
- blocker / next action / risk level 展示
- 当前是否等待审批的展示

### 5.4 飞书审批决策层

负责：

- 承接自动化抛出的人工选择题
- 展示候选方案与风险说明
- 输出最终选择结果
- 为后续执行提供正式决策锚点

## 6. 目标驱动进度模型

### 6.1 目标层

目标层用于表达“我们在推进什么，以及整体卡在哪”。

建议状态示例：

- `planned`
- `active`
- `blocked`
- `waiting_decision`
- `ready_for_release`
- `released`

目标层不直接承载底层执行细节，而是聚合任务结果。

### 6.2 任务层

任务层沿用并扩展现有四层状态模型：

- `implementation_status`
- `platform_status`
- `governance_status`
- `automation_status`

同时增加审批相关语义：

- `risk_level`
- `approval_status`
- `approval_decision_id`
- `approval_due_at`
- `decision_summary`

### 6.3 目标与任务关系

关系规则如下：

- 一个目标可以关联多个任务
- 一个任务必须归属于一个主目标
- 目标状态由任务状态聚合得到，但不能简单相加
- 若任一关键任务进入 `waiting_decision`，目标层应能直接暴露该状态

## 7. 飞书 Base 结构设计

### 7.1 目标推进表

建议新增一张 `目标推进表`，最少字段如下：

- `goal_id`
- `goal_name`
- `goal_owner`
- `goal_status`
- `goal_progress`
- `current_phase`
- `key_blocker`
- `next_milestone`
- `risk_level`
- `latest_decision_summary`
- `updated_at`

用途如下：

- 给用户看全局推进
- 识别哪个目标卡住
- 判断当前优先级和下一阶段

### 7.2 自动化任务监控表

现有 `自动化任务监控` 表应扩展为正式任务层视图，建议字段分组如下：

基础标识：

- `task_id`
- `task_name`
- `goal_id`
- `repo`
- `branch`
- `pr_number`

执行状态：

- `implementation_status`
- `platform_status`
- `governance_status`
- `automation_status`

协作状态：

- `blocker`
- `next_action`
- `last_comment_anchor`
- `last_commit`

审批状态：

- `risk_level`
- `approval_status`
- `approval_decision_id`
- `approval_due_at`
- `decision_summary`

干预入口：

- `remote_action`
- `remote_action_result`
- `updated_at`

### 7.3 字段约束

- `platform_status` 只能来自 GitHub 真源
- `governance_status` 不能在飞书手工改写
- `approval_status` 只能由审批桥接逻辑回写
- `decision_summary` 必须是正式可追溯摘要，不能只写“已处理”
- `risk_level` 至少区分：
  - `low`
  - `medium`
  - `high`
  - `critical`

## 8. 风险审批模型

### 8.1 审批的角色定位

审批只承接“需要用户做选择”的时刻，不承接持续监控。

审批的核心问题不是“状态是什么”，而是：

- 当前出现了什么分叉
- 有哪些候选方案
- 系统推荐哪一个
- 用户最终选择哪一个

### 8.2 必须触发审批的场景

第一版建议以下场景必须触发审批：

- 多个可行方案会影响后续路线或资产结构
- 从单任务扩展为多 agent 协作
- 恢复已暂停的自动化主链
- 进入 `release / released` 前的最终放行
- 执行回滚、覆盖、重跑高成本链路
- 目标优先级调整或主目标切换

### 8.3 默认不触发审批的场景

以下场景默认由自动化自主推进：

- 最小改动修复
- 明显低风险的局部实现路径
- 复用既有模式且测试易验证的修改
- 回滚成本低、影响范围小的调整

## 9. 审批单结构设计

每次审批实例必须对应一个 `decision_id`。

审批单至少包含：

- `decision_id`
- `goal_id`
- `task_id`
- `trigger_reason`
- `risk_level`
- `recommended_option`
- `options`
- `impact_scope`
- `rollback_strategy`
- `due_at`
- `timeout_fallback`

其中 `options` 至少要包含：

- 方案名称
- 方案说明
- 收益
- 风险
- 回滚方式

审批单的目标不是“写一堆说明”，而是把选择题结构化。

## 10. 最佳方案与保守策略规则

### 10.1 最佳方案判定

低风险自动推进时，沿用以下优先级：

1. 最小改动
2. 复用现有实现模式
3. 测试最容易验证
4. 回滚成本最低
5. 对既有文档和协作链影响最小

### 10.2 审批超时后的保守策略

当审批在 `due_at` 前未被处理时，系统按以下顺序决策：

1. 若存在“最保守、可回滚、低扩张”的备选方案，则自动执行该方案
2. 若不存在足够安全的保守方案，则回写：
   - `approval_status=timeout`
   - `automation_status=paused`
   - `decision_summary=waiting_for_manual_decision`

### 10.3 禁止的超时处理

审批超时后，禁止以下行为：

- 自动选择最激进方案
- 自动扩大为多 agent 并行
- 自动进入 release
- 自动覆盖已有资产或改写关键治理结论

## 11. 数据流设计

### 11.1 GitHub -> 飞书进度表

bridge 读取 GitHub 真源状态：

- PR
- checks
- workflow run
- 结构化评论
- 最近 commit

随后：

- 回写任务监控表
- 聚合生成目标推进表状态

### 11.2 Dream-Agent -> 飞书审批

当编排层识别到高风险分叉或关键节点时：

- 生成 `decision_id`
- 输出推荐方案与备选方案
- 创建审批实例
- 在任务表中回写：
  - `approval_status=pending`
  - `approval_decision_id=<decision_id>`
  - `approval_due_at=<timestamp>`

### 11.3 飞书审批 -> 执行决策

审批完成后：

- bridge 读取审批结果
- 映射为明确动作
- 更新任务表 `decision_summary`
- 继续 GitHub / Dream-Agent 后续执行

### 11.4 超时回写

若审批超时：

- 先执行保守方案，或
- 回写为等待人工决策

随后同步更新：

- 任务表
- 目标推进表
- 必要时 GitHub 评论锚点

## 12. 状态映射规则

### 12.1 审批状态

建议 `approval_status` 至少包含：

- `not_required`
- `pending`
- `approved`
- `rejected`
- `timeout`
- `executed`

### 12.2 目标等待决策状态

当满足以下任一条件时，目标层应聚合显示为 `waiting_decision`：

- 存在关键任务 `approval_status=pending`
- 存在关键任务 `approval_status=timeout` 且仍未人工接手
- 存在关键任务因审批结果被显式暂停

### 12.3 审批与四层状态的关系

- 审批不会直接覆盖 `platform_status`
- 审批不会直接覆盖 `governance_status`
- 审批只决定“下一步做什么”
- 真正执行后产生的新状态，仍要由 GitHub 真源回写

## 13. 用户视角工作流

用户在飞书中的典型使用方式如下：

1. 打开 `目标推进表` 看当前主目标推进情况
2. 识别某个目标的 `risk_level / blocker / latest_decision_summary`
3. 下钻到 `自动化任务监控` 表，看具体任务四层状态
4. 若任务正在等待拍板，则进入对应审批单
5. 审批结果回写后，继续观察任务是否恢复推进

这样用户不会被迫反复切换 GitHub 与聊天记录才能理解当前局面。

## 14. 实施顺序

推荐按以下顺序落地：

1. 扩展 `自动化任务监控` 表，补审批相关字段
2. 新建 `目标推进表`
3. 实现任务 -> 目标 的聚合映射
4. 设计审批实例结构与结果读取桥接
5. 定义高风险分叉识别规则
6. 接入审批超时后的保守策略
7. 以单目标、单链路先做试运行

## 15. 验收标准

第一版完成后，必须同时满足：

### 15.1 进度可见性

- 用户能在飞书中看到目标推进表
- 用户能从目标下钻到任务
- 用户能识别当前 blocker、next action、risk level

### 15.2 审批可用性

- 高风险分叉能生成审批单
- 审批单包含候选方案、推荐方案、风险和回滚说明
- 审批结果能回写任务状态

### 15.3 超时策略正确

- 审批超时后不会走激进路径
- 有保守方案时自动续跑
- 无保守方案时自动暂停并等待人工决策

### 15.4 状态一致性

- GitHub 真源状态与飞书展示一致
- 不允许出现“审批通过但 GitHub 真状态未更新却被误显示为完成”
- 不允许出现“目标层已显示 released，但底层任务仍未通过 checks”

## 16. 非法状态与禁止事项

禁止以下情况：

- 用审批代替实时监控
- 在飞书手动改写 GitHub 真状态
- 审批超时后自动走高风险方案
- 目标层与任务层口径不一致
- 未给出回滚方式就发起高风险审批
- 未建立目标聚合前就只靠审批单承载整体推进状态

## 17. 完成后的系统形态

本设计完成后，系统应达到以下形态：

- GitHub 是执行真源
- 飞书 Base 是目标驱动的实时监控面
- 飞书审批是高风险分叉与关键节点的人工决策闸门
- Dream-Agent 是识别分叉、生成选项、读取结果并继续执行的编排内核
- 自动化既不会因为所有小事都等审批而停滞，也不会在关键选择上失控放大
